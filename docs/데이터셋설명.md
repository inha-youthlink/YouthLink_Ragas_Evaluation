# 평가 데이터셋 설명

평가에 쓰는 데이터셋의 종류, 구성 기준, 만드는 과정을 정리한 문서다. 세부 생성 규격은 `docs/RAGAS_PRD.md` "데이터셋 생성"·"프로필 채우기", `docs/RETRIEVE_PRD.md` "데이터셋"을 따른다.

## 1. 데이터셋 종류

| 데이터셋 | 파일 | 평가 | 샘플 유형 | 기대값 |
| --- | --- | --- | --- | --- |
| golden | `datasets/golden_vN.jsonl` | 답변 품질(RAGAS) + 검색 적중률 | 정책 하나를 묻는 구체적인 질문 한 종류 | 정답 문장, 정답 정책, 정책 원문 |
| routing | `datasets/routing_vN.jsonl` | 라우팅 (질문 유형 분류) | 유형 7종이 섞여 있음 | 기대 유형 (`expected_intent`) |

> 평가 종류마다 데이터셋을 따로 둔다. 한 데이터셋 안에는 한 가지 목적의 샘플만 넣어, 점수가 무엇을 뜻하는지 섞이지 않게 한다.

## 2. golden 데이터셋

### 구성 기준

golden은 RAG가 검색해서 정답 정책을 찾아야만 답할 수 있는 정책 질문으로만 구성한다.

| 항목 | 내용 |
| --- | --- |
| 질문 | 정책 문서 하나의 구체적인 내용(지원 금액, 자격 조건, 신청 방법 등)을 묻는 질문. 일반 상식으로 답할 수 있는 질문은 넣지 않음 |
| 정답 | 그 정책 원문에서 뽑은 문장 |
| 기대 경로 | 모든 샘플이 검색 핸들러(`search`)로 가서 근거로 답하는 것. 그래서 샘플마다 기대 유형을 적지 않음 |
| 기대 경로와 다른 응답 | 짧은 답변(`short`)은 RAG 분류 오류, 되묻기(`clarify`)는 프로필·조건 추출 또는 질문 모호성 문제로 보고 채점과 따로 집계 |
| 검수에서 제외 | 모호한 질문, 같은 이름의 정책이 여러 개인 질문, 정답이 틀린 질문 (스킬 검수 + 사용자 승인) |
| 검색 필요성 확인 | RAG 없이 LLM에 질문만 보낸 `baseline` 점수가 RAG보다 크게 낮아야 함. baseline 점수가 높은 샘플은 상식 질문인지 검토 |

> golden은 "정답 정책을 찾아야만 맞힐 수 있는 질문"의 모음이다. 응답이 검색 경로를 타지 않았다면 데이터셋이 아니라 RAG의 분류·조건 처리 결과로 본다.

### 만드는 과정

```
서비스 DB policy ──generate──▶ 후보 ──profile──▶ 프로필 붙은 후보 ──스킬 검수 + 사용자 승인──▶ golden_vN
```

| 단계 | 하는 일 | LLM 비용 |
| --- | --- | --- |
| ① 생성 (`generate`) | 정책 1건을 문서 1개로 만들어 TestsetGenerator에 넣고, 질문·정답·근거 원문을 생성 | 있음 |
| ② 프로필 추가 (`profile`) | 후보마다 정답 정책의 지역·나이 조건과 질문 내용에 맞춰 프로필을 채우고, 확신할 수 없는 샘플은 검수 대상으로 표시 | 없음 |
| ③ 검수 (`ragas-dataset-review` 스킬) | Claude가 정책 원문과 대조해 질문·정답과 프로필을 함께 판정하고 검수표를 만듦 | 없음 (LLM API 미사용) |
| ④ 확정 | 사용자가 검수표를 보고 승인한 샘플만 `golden_vN.jsonl`로 확정 | 없음 |

> 질문·정답은 TestsetGenerator로 만들고, 검수 전에 프로필까지 붙여서 검수와 승인을 한 번에 끝낸다. 확정본은 수정하지 않으므로 바꿀 때는 새 버전을 만든다.

`golden_v1`은 프로필 없이 먼저 확정되어, 같은 질문에 프로필만 붙인 `golden_v2`를 따로 만든다. 질문·정답·정답 정책이 같아서 두 버전의 점수 차이는 프로필(1차 필터)의 영향으로 읽을 수 있다.

### 프로필

| 항목 | 내용 |
| --- | --- |
| 채우는 값 | 지역(`region_code`, 시도 전체 `XX000`)과 나이(`age`)만 |
| 지역 | 질문에 시도 이름이 있으면 그 시도, 정책 지역이 한 시도면 그 시도, 여러 시도(전국 포함)면 샘플마다 돌려 씀 |
| 나이 | 기본 25세를 정책 나이 범위에 맞춤. 질문에 "20대 후반" 같은 나이대가 있으면 그 안의 나이 |
| 넣지 않는 경우 | 정답이 "자격 없음" 판정인 샘플 |
| 다른 항목을 비우는 이유 | 취업 상태·학력 등이 질문 속 상황과 어긋나면 RAG가 답변 끝에 차이를 안내해 정답과 멀어짐 |

> 프로필은 "정답 정책이 필터를 통과할 수 있고, 질문 내용과도 어긋나지 않는 사용자"로 만든다. 그래야 필터·검색에서 정답이 빠졌을 때 데이터셋이 아니라 RAG 문제로 판단할 수 있다.

### 필드

| 필드 | 내용 |
| --- | --- |
| `sample_id` | 샘플 번호 (`single-000123`) |
| `policy_no` | 정답 정책 번호 (검색 적중률 기준) |
| `question` | 질문 |
| `ground_truth` | 정답 문장 |
| `reference_contexts` | 정답의 근거가 된 정책 원문 |
| `synthesizer_name` | 생성 방식 (`single_hop_specific_query_synthesizer`) |
| `profile` | RAG에 보낼 프로필. RAG `Profile` 필드만 허용, 빈 값은 보내지 않음 |
| `source_updated_at` | 생성 당시 정책 수정 시각. 그 뒤 정책이 바뀐 샘플은 평가에서 제외 |
| `reviewed` | 검수 통과 여부. `true`만 평가에 씀 |

> 질문과 함께 정답 문장·정답 정책·정책 원문을 담아, 답변 품질(정답·원문과 비교)과 검색 적중률(정답 정책을 찾았는지)을 한 데이터셋으로 잰다.

## 3. routing 데이터셋

| 항목 | 내용 |
| --- | --- |
| 목적 | RAG가 질문 유형을 맞게 분류하는지 확인 |
| 유형 | `policy_list`, `policy_detail`, `eligibility`, `comparison`, `chitchat`, `out_of_scope`, `unclear` (7종, 각 10~15건) + 하위 질문이 여러 개인 질문 |
| 필드 | `sample_id`(`route-000001`), `question`, `expected_intent`(하위 질문마다 1개), `reviewed`, `note`(선택, 경계 사례 판정 근거) |
| 작성 | 초안을 쓰고 사람이 검수 (LLM API 호출 없음) |
| 판정 기준 | RAG 분석 프롬프트의 유형 정의를 따름. 해석이 갈리는 질문과 프롬프트 예시 질문은 넣지 않음 |
| 보내는 방식 | 대화·프로필 없이 질문만 |

> routing은 정답 문장 없이 기대 유형만 담는다. 답변 품질이 아니라 "질문을 어떤 처리로 보낼지"를 맞게 판단했는지만 본다.

## 4. 아직 없는 데이터셋

| 대상 | 필요한 이유 | 필요한 것 |
| --- | --- | --- |
| 되묻기가 정답인 질문 | 프로필과 다른 지역·나이를 말한 질문(예: 서울 프로필 + "인천 창업 지원 알려줘")에 RAG가 제대로 되묻는지 확인 | 기대 경로 필드(예: `expected_handler`)를 golden에 둘지, 별도 데이터셋으로 만들지 결정 |
| 여러 정책을 비교·나열하는 질문 | golden은 정책 하나를 묻는 질문뿐이라 비교·목록 질문의 답변 품질은 재지 않음 | 정답 정책이 여러 개인 샘플 형식 |
| 이어지는 대화 | 앞 턴 카드를 가리키는 질문(`detail` 핸들러)은 평가하지 않음 | 앞 턴(`history`)·현재 정책을 담는 샘플 형식 |

> 지금 데이터셋은 "정책 하나를 묻는 단일 질문"과 "질문 유형 분류"만 다룬다. 되묻기·비교·대화 흐름은 필요해지면 따로 만든다.
