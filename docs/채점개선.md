# RAG 변경에 따른 평가 방식 정리

RAG에 프로필 1차 필터와 핸들러 분기가 들어오면서, 평가 데이터셋과 채점 방식을 그에 맞게 바꾼 내용이다.

## 1. 배경: RAG가 어떻게 바뀌었나

| 항목 | 기존 RAG | 개선된 RAG |
| --- | --- | --- |
| 처리 흐름 | 질문 → 검색 → 답변 (단일 체인) | 질문 분석 → 프로필로 1차 필터 → 핸들러 분기 → 답변 |
| 정책 거르기 | 없음 (전체 정책에서 검색) | 사용자 프로필(지역·나이 등)에 맞는 정책만 남김 |
| 응답 종류 | 항상 근거 있는 답변 | 근거 답변, 짧은 답변, 되묻기 문구 |
| 서비스 입력 | 질문 | 질문 + 프로필 (서비스에서는 프로필이 필수) |

> 기존에는 단일 RAG 체인이라 모든 질문이 근거를 포함한 답변을 반환했다. 필터링과 라우팅(핸들러 분기)이 도입되면서 질문이 프로필 조건으로 걸러지고, 모든 답변이 근거 있는 답변은 아니게 되었다.

## 2. 기존 평가 방식의 문제점

| # | 기존 평가 | 왜 비현실적이었나 | 결과 |
| --- | --- | --- | --- |
| 1 | 데이터셋에 질문·정답만 있고 프로필이 비어 있음 | 빈 프로필이면 RAG가 1차 필터를 건너뛴다. 실제 사용자는 프로필이 항상 있어서 타지 않는 경로다 | 필터 없이 정책 전체를 검색한 점수라 실제 서비스 성능으로 볼 수 없음 |
| 2 | 1차 필터를 측정하지 않음 | 필터가 정답 정책을 잘못 빼도 알 수 없다 | `filter_hit`가 전부 NULL. 깔때기 4단계(필터 → 검색 → 후보 → 카드) 중 3단계만 측정 |
| 3 | 모든 응답을 지표 7개로 채점 | 단일 체인에서는 응답에 항상 근거가 있어 문제가 없었지만, 핸들러 분기 후에는 근거 없는 응답도 들어온다 | 짧은 답변·되묻기 문구까지 채점하면 근거 기반 지표가 0점·실패로 나와 평균이 왜곡됨 |

> 기존 평가는 프로필 없이 질문만 보내서 실제 사용자가 타지 않는 "필터 없는 경로"를 측정했고, 응답 종류를 구분하지 않아 근거 없는 응답까지 채점했다. 그래서 점수가 실제 서비스 성능을 대표하지 못했다.

## 3. 데이터셋 생성 과정에서 바뀐 것

| 단계 | 기존 | 지금 | 추가된 이유 |
| --- | --- | --- | --- |
| ① 질문·정답 생성 | TestsetGenerator로 정책에서 질문, 정답, 근거 원문 생성 | 같음 | |
| ② 사람 검수 | 모호하거나 정답이 틀린 샘플 제외 → `golden_v1` 100건 | 같음 | |
| ③ 프로필 추가 | 없음 | `profile` 명령으로 지역(`region_code`, 시도 전체 `XX000`)·나이(`age`)를 채움 | 실제 서비스처럼 1차 필터를 거치게 하려고 |
| ④ 프로필 검수 | 없음 | 자동으로 확신할 수 없는 샘플을 사람이 판단 (golden_v1 기준 11건) | 질문의 "NN세"가 본인 나이인지 자격 범위인지 등은 기계가 정할 수 없음 |
| ⑤ 확정 | `golden_v1.jsonl` | `golden_v2.jsonl` (v1은 수정하지 않음) | |
| 형식 검사 | 없음 | `profile`은 RAG `Profile` 필드와 형식만 허용 | 오타로 필터가 조용히 꺼지는 것을 막으려고 |

> 질문·정답을 만드는 과정(TestsetGenerator + 사람 검수)은 그대로이고, 그 뒤에 프로필을 채우고 검수하는 단계가 추가되었다. 질문·정답·정답 정책은 v1과 같으므로 v1과 v2의 점수 차이는 1차 필터의 영향으로 읽을 수 있다.

프로필은 아무 값이나 넣지 않고 정답 정책을 기준으로 넣는다.

| 원칙 | 이유 |
| --- | --- |
| 정답 정책의 지역·나이 조건 안에서 고르기 | 조건 밖이면 필터가 정답을 빼는 것이 정상이라 오답처럼 보인다 |
| 질문에 나온 지역·나이와 맞추기 | 다르면 RAG가 "조건이 다르다"며 되묻는다 |
| 정답이 "자격 없음"이면 프로필을 넣지 않기 | 프로필을 넣으면 필터가 그 정책을 빼서 질문 자체가 성립하지 않는다 |

> 프로필은 "정답 정책이 필터를 통과할 수 있고, 질문 내용과도 어긋나지 않는 사용자"로 만든다. 그래야 필터·검색에서 정답이 빠졌을 때 데이터셋 문제가 아니라 RAG 문제로 판단할 수 있다.

## 4. 응답을 보고 평가 여부를 정하는 기준

RAG 응답의 `trace.handler`를 보고 정한다.

| `trace.handler` | 응답 | RAGAS 지표 7개 | 검색 적중률 | 보고서 |
| --- | --- | --- | --- | --- |
| `search` | 검색한 근거로 답변 | 7개 전부 | 4단계 전부 | 일반 |
| `detail` | 지목한 정책의 근거로 답변 | 7개 전부 | 계산 | 일반 (golden은 한 턴짜리라 나오지 않음) |
| `short` | 근거 없는 짧은 답변 (인사·범위 밖) | 답변 지표 4개만. 근거 기반 3개는 NULL | 계산하지 않음 | "짧은 답변" 섹션 (golden 질문에서 나오면 분류 오류) |
| `clarify` | 되묻기 고정 문구 | 채점하지 않음 | 계산하지 않음 | "되묻기 응답" 섹션 (`clarify_reason`별 건수) |

> RAGAS의 근거 기반 지표는 근거가 있는 답변에서만 의미가 있다. 그래서 되묻기 문구는 채점에서 빼고, 짧은 답변은 근거 기반 지표만 빼고 답변 지표로 채점한다. 둘 다 보고서에 따로 모아서 보여 준다.

지표를 나눈 기준은 다음과 같다.

| 지표 묶음 | 지표 | 비교 대상 | 근거 없는 응답에서 |
| --- | --- | --- | --- |
| 답변 지표 | `answer_relevancy`, `factual_correctness`, `reference_faithfulness`, `answer_coverage` | 답변 ↔ 질문, 정답, 정책 원문 | 계산 가능 |
| 근거 기반 지표 | `context_precision`, `context_recall`, `faithfulness` | RAG가 검색한 근거 (`trace.contexts`) | 근거가 없어 의미 없음 |

> 답변 지표는 데이터셋의 정답·원문과 비교하므로 어떤 응답에도 계산할 수 있다. 근거 기반 지표는 RAG가 가져온 근거가 있어야 계산할 수 있다.

헷갈리기 쉬운 경우는 다음과 같이 처리한다.

| 경우 | 처리 | 이유 |
| --- | --- | --- |
| 검색은 했는데 결과가 0건 | 7개 모두 채점 | 실제 검색 실패라 낮은 점수가 맞다 |
| 1차 필터를 걸지 않은 응답 | `filter_hit`만 NULL | 판정할 수 없는 것이지 0점이 아니다 |
| 지표 계산 실패 | 그 지표만 NULL, `metadata.errors`에 기록 | 0점으로 채우지 않는다 |

> 점수를 뺄지는 "응답이 근거를 가졌는가"로 정하고, 0과 NULL을 구분한다. 0은 실패이고, NULL은 판정할 수 없다는 뜻이며 평균에서 빠진다.
